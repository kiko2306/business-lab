# SSH key access to the server

Password authentication is disabled on this host. Access is by key, or through
the browser terminal.

There are three ways in, and it is worth knowing all three before changing
anything — the whole point of having more than one is that hardening SSH can
never lock you out.

| | How | When you'd use it |
|---|---|---|
| **Browser terminal** | `https://ssh.<base-domain>` (Authelia login) | From any network, including ones that block outbound SSH. Needs no key on the client. |
| **CLI over NetBird** | `ssh mat@100.111.227.79` | Normal day-to-day admin from an enrolled device. |
| **CLI on the LAN** | `ssh mat@192.168.1.23` | At home, no VPN needed. |

The browser terminal authenticates with its own key, generated by `start.sh`
and never leaving the server (see [Why this is safe](#why-this-is-safe)). It is
unaffected by anything you do to your personal keys, which is what makes it a
reliable fallback.

## Add a laptop (or any client)

Do these in order. Steps 1–2 are on the **laptop**, step 3 on the **server**.

### 1. Generate a keypair on the laptop

Never generate it on the server. A private key should be created on the machine
that will use it and never travel anywhere.

```bash
ssh-keygen -t ed25519 -C "$(whoami)@$(hostname)"
```

Accept the default path (`~/.ssh/id_ed25519`). A passphrase is optional but
recommended — it means a stolen laptop doesn't hand over server access.

On Windows, use PowerShell; the command is identical and the key lands in
`C:\Users\<you>\.ssh\`.

### 2. Copy the PUBLIC key

```bash
cat ~/.ssh/id_ed25519.pub
```

One line, starting `ssh-ed25519 AAAA…`. That is the half that is safe to copy,
paste, and email. **Never** share `id_ed25519` (no `.pub`) — that is the secret.

### 3. Install it on the server

If you can already SSH in, one command does it:

```bash
ssh-copy-id mat@100.111.227.79
```

Otherwise — including the first time, or if you're locked out of CLI access —
open **`https://ssh.<base-domain>`** in a browser, log in through Authelia, and
paste:

```bash
echo 'ssh-ed25519 AAAA... you@laptop' >> ~/.ssh/authorized_keys
```

Then fix permissions. `sshd` silently ignores `authorized_keys` if they are too
open, which looks exactly like a rejected key:

```bash
chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys
```

### 4. Test it

From the laptop:

```bash
ssh -o PasswordAuthentication=no mat@100.111.227.79 'echo OK'
```

`OK` means the key works. If it doesn't, nothing is lost — the browser terminal
is unaffected by any of this, so you can go back and fix `authorized_keys`
there.

## Turning password authentication off

**You do not need a laptop key first.** The browser terminal authenticates by
key, not password, so disabling password authentication does not affect it —
it stays available throughout, and it is what stops this from ever being a
lockout risk. Adding a laptop key is about CLI convenience, and can happen
before or after.

Keep the browser terminal open while you reload `sshd`, as ordinary care rather
than because passwords matter to it.

### The drop-in ordering trap

`/etc/ssh/sshd_config` includes `/etc/ssh/sshd_config.d/*.conf`, and **in sshd
the first value obtained wins** — not the last. This is the opposite of most
config systems and catches people out.

Ubuntu images ship `50-cloud-init.conf` containing `PasswordAuthentication yes`.
A file named `99-no-password.conf` sorts *after* it and is therefore **ignored**.

Name yours so it sorts first:

```bash
echo 'PasswordAuthentication no' | sudo tee /etc/ssh/sshd_config.d/00-no-password.conf
sudo systemctl reload ssh
```

### Verify it actually applied

Do not trust the file's presence — check the effective config:

```bash
sudo sshd -T | grep -i passwordauthentication
```

Must print `passwordauthentication no`. If it prints `yes`, something earlier
still wins; check every file in `/etc/ssh/sshd_config.d/` and any
`PasswordAuthentication` line appearing *before* the `Include` in
`/etc/ssh/sshd_config`.

A second, independent check — the rejection message lists the methods the
server accepts:

```bash
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no nobody@192.168.1.23
```

- `Permission denied (publickey)` → password auth is genuinely off.
- `Permission denied (publickey,password)` → it is **still enabled**.

## Remove a key

Keys are one line each in `~/.ssh/authorized_keys`. To revoke a lost laptop,
delete its line — identify it by the trailing comment:

```bash
grep -n '' ~/.ssh/authorized_keys      # list with line numbers
sed -i '3d' ~/.ssh/authorized_keys     # delete line 3
```

Do not delete the `wetty@…` line unless you intend to break the browser
terminal.

## Why this is safe

The browser terminal's key is generated by `start.sh` on the server, and its
private half never leaves the machine — the terminal container runs on this
same host and connects back to it, so both ends of that hop are local. Nothing
is transmitted, which is why it can be fully automated while your personal keys
cannot.

That key is also what makes disabling password authentication safe: browser
access keeps working whether or not any particular laptop has a working key.
